# DeviceConfig fault localization

Diagnosis (source and tests unchanged):

- `src/misc/DeviceConfig.ts:68-111`: `_load()` unconditionally calls `_writeToStorage()` at line 90 whenever JSON loaded, even if `_version` is current and `_signupToken` exists. That call happens before `_scheduledAlarmUsers`, `_language`, `_defaultCalendarView`, `_hiddenCalendars`, `_signupToken`, `_testDeviceId`, and `_testAssignments` are restored. `JSON.stringify(this)` at lines 161-172 omits these undefined fields, so a current config can be overwritten with a partial document. A missing token causes a second write after full loading, but the first write is still destructive if interrupted.
- `src/misc/DeviceConfig.ts:260-311`: migration's current-version guard compares the object itself to `ConfigVersion`. V2-to-V3 leaves `_credentials` as an array and never sets `_version`; `_load()` then builds a Map keyed by array indexes via `typedEntries`, so `loadByUserId` cannot find migrated credentials. V1 migration replaces `_credentials` with an empty array, discarding any old entries. V2 conversion uses `mailAddress.includes("@")`, so malformed/missing mailAddress can throw. Existing migration test asserts the array form and covers only direct V2 conversion.
- `src/misc/DeviceConfig.ts:68-121`: `getItem` exceptions are uncaught, valid JSON of the wrong shape can fail migration/deserialization, and missing/invalid config token creation relies on `window.crypto` being present. This can prevent graceful default initialization. `_credentialEncryptionMode` and `_encryptedCredentialsKey` may remain undefined if absent.
- `src/misc/DeviceConfig.ts:14-38,161-172,313`: persisted fields are separate class properties and serialization uses the entire instance, so the required single config object and explicit `DeviceConfig.Version` / `DeviceConfig.LocalStorageKey` API are absent. Global instance construction has no explicit version or storage parameters.
- `src/misc/DeviceConfig.ts:41-51`: `store()` already retains an existing nonempty `databaseKey` when replacing credentials; preserve that behavior while moving credentials into the config object.

Suggested fix scope: build a complete config with all twelve exact underscored persisted keys before any write; migrate old credential arrays to objects keyed by userId and deserialize to Map; track whether migration or token creation changed content and write once only then; serialize the config object alone; inject storage/version into constructor and use static public constants; guard read failures and malformed input. Add load/idempotence tests using storage spy and round-trip tests for every recognized field, V1/V2 migration, malformed JSON, unavailable storage, and token generation. Uncertainty: no test currently documents the precise V1 credential shape or behavior under a missing browser crypto implementation.
