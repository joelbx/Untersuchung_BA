The confirmed defect is in [WebKit `CertificateErrorWrapper.__init__`](/app/qutebrowser/browser/webkit/certificateerror.py:33): it accepts only `errors`, so `reply=...` raises `TypeError`. [`on_ssl_errors`](/app/qutebrowser/browser/webkit/network/networkmanager.py:251) receives both values but passes only the errors. The fix should accept and retain the reply without starting network activity during construction, while preserving error based equality and hashing.

HTML rendering already follows the requested shape: the [shared `html()` method](/app/qutebrowser/utils/usertypes.py:497) escapes a single error in `<p>`, and the [WebKit override](/app/qutebrowser/browser/webkit/certificateerror.py:56) renders multiple errors in `<ul>` with Jinja autoescaping. All four [existing HTML tests](/app/tests/unit/browser/webkit/test_certificateerror.py:35) pass. They do not cover named reply arguments, empty errors, or special characters beyond angle brackets.

The requested decision API, `UndeferrableError`, Qt5/Qt6 WebEngine subclasses, and factory are also absent from [the shared abstraction](/app/qutebrowser/utils/usertypes.py:484) and [WebEngine wrapper](/app/qutebrowser/browser/webengine/certificateerror.py:28). Their intended decision and deferral semantics need care because the current WebEngine callers use a mutable `ignore` flag. Per the fault-localization constraint for this task, I left project source and tests unchanged.
