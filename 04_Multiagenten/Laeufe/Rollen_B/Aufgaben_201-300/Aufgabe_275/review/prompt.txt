ISSUE:
**Title:** Correctly classify proxy authentication errors for Kubernetes requests

**Description**

The Kubernetes proxy currently surfaces every error produced while building the
authentication context as an access-denied error. This masks the original type of
non-authorization failures and prevents callers from distinguishing authorization
failures from lookup or setup failures.

**Actual Behavior**

`authenticate` converts every `setupContext` failure into `AccessDenied`.

**Expected Behavior**

`authenticate` must preserve the distinction between access-related and unrelated
errors:

- An authorization failure and an unsupported user type are access-related and
  must be returned as `AccessDenied` (`trace.IsAccessDenied(err) == true`).
- An unknown Kubernetes cluster in the local cluster is not access-related and
  must remain a non-`AccessDenied` lookup/not-found-style error.
- A remote-cluster request made by a process without a reverse tunnel is not
  access-related. The underlying `setupContext` error is `BadParameter`; it must
  remain non-`AccessDenied` (`trace.IsAccessDenied(err) == false`).
- Non-access errors may be wrapped, but their trace classification must be
  preserved.


REQUIREMENTS:
- `authenticate` must return `AccessDenied` only when the underlying failure is
  access- or authorization-related.

- The following cases must satisfy `trace.IsAccessDenied(err) == true`:
  - an authorization failure reported by the authorization layer;
  - an unsupported user type in the resolved authentication context.

- The following cases must satisfy `trace.IsAccessDenied(err) == false`:
  - an unknown Kubernetes cluster referenced in the local cluster;
  - a remote-cluster request that cannot be served because the current process has
    no reverse tunnel. This case originates as `trace.BadParameter` and must not be
    reclassified as `AccessDenied`.

- When `setupContext` returns a non-access error, `authenticate` must preserve or
  wrap the original error rather than replacing it with `AccessDenied`.

- The implementation must not change `setupContext` merely to force a desired
  classification at the caller. In particular, the existing no-tunnel
  `BadParameter` classification must be preserved.

- Callers must be able to distinguish the two categories reliably with
  `trace.IsAccessDenied(err)`.
