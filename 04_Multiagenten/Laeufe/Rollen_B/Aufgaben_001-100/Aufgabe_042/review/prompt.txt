ISSUE:
#title: Add a basic webfinger implementation at /.well-known/webfinger

**Issue Description** Federated identity discovery via the `.well-known/webfinger` endpoint is not currently supported. Requests to `.well-known/webfinger` result in a 404 since no such endpoint exists.

**Current Behavior** No handler exists for `/.well-known/webfinger`; clients requesting it receive a 404.

**Expected Behavior** The application should serve valid WebFinger responses at `/.well-known/webfinger`, allowing compliant clients to discover user identity metadata. The endpoint must validate the `resource` query parameter, enforce authorization based on the `groups:view:users` global permission (evaluating anonymous requests as the Guest role), resolve the requested user, and return a structured JSON response conforming to the WebFinger standard (subject, aliases, links).

REQUIREMENTS:
- A new route should be registered at /.well-known/webfinger that returns JSON responses for federated identity discovery. The output must conform to the WebFinger standard including subject, aliases, and links. - The WebFinger handler must validate the resource query parameter. If it is missing, does not begin with acct:, or does not end with the expected hostname from nconf.get('url_parsed').hostname, it must return a 400 Bad Request. If the user identified by the username portion of the resource cannot be resolved, a 404 Not Found must be returned. - If the requesting user (req.uid) lacks the groups:view:users global permission, the endpoint should return 403 Forbidden. When req.uid is absent (anonymous), authorization should be evaluated as the Guest role. - On valid requests, the `/.well-known/webfinger` endpoint should return a structured JSON response that includes the subject field set to the original "resource" string, an "aliases" array containing both UID-based and slug-based user profile URLs, and a links array that includes at least one entry referencing the user's HTML profile page (e.g., the canonical /user/<slug> URL). The specific rel and type values in links are not constrained. - The WebFinger handler logic should live in a dedicated controller file `src/controllers/well-known.js`, and the endpoint should be mounted via a router file `src/routes/well-known.js` integrated into the application's main route composition so it is available at app startup. - For unauthenticated requests (req.uid is absent), access to `/.well-known/webfinger` should be evaluated under the Guest role. Authorization should depend on the groups:view:users global permission assigned to that role. If the Guest role does not have groups:view:users, the endpoint should return 403 Forbidden. This check should be implemented in the WebFinger handler in src/controllers/well-known.js using the existing privileges API.

INTERFACES:
1) Controller: WebFinger handler Name: webfinger Type: Function Location: src/controllers/well-known.js Input: req: Request (expects query param resource) res: Response Output: HTTP 200 with JSON { subject, aliases, links } on success HTTP 400 / 403 / 404 on validation/authorization/not-found cases Description: Handles GET /.well-known/webfinger. Validates resource, checks authorization, resolves the username (slug) to a UID, and returns a structured WebFinger JSON payload (subject set to the original resource, aliases with UID- and slug-based URLs, and links including an entry for the user's HTML profile). When req.uid is absent, authorization should be evaluated as the Guest role, and access should be gated by the groups:view:users global permission.

Integrated into the main route composition, so it's mounted at app startup.
